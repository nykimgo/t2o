## 0. 압축판 (매 프롬프트에 붙이는 3~5줄)

```
[맥락]
- 프로젝트: 사전시각화(프리비즈) 프로젝트. 본 제작 착수 전에 장면 구성·동선·카메라를
  저비용으로 검증할 수 있도록, 스토리보드·대본에서 USD 프리비즈 씬을 자동 구성한다.
- 파이프라인: 스토리보드·대본 → 의도 분석 모듈(LLM, 타 담당) → 에셋 검색 모듈
  → [내 담당: 3D 객체 생성 모듈] → 공간(배경) 생성 모듈(타 담당)
- 전 구간이 USD로 관리되며 모든 모듈의 입출력이 USD다.
- 내 모듈의 위치: 검색 모듈이 DB에서 쓸만한 에셋을 못 찾았을 때만 생성한다.
  즉 생성은 검색의 폴백이지 기본 경로가 아니다.
- 내 범위: 사람 에셋을 제외한 전부. 사물뿐 아니라 갈매기·강아지 같은 생물도 포함되며
  생물은 리깅이 필요하다. 사람 에셋만 별도 담당자가 있다.
- 리깅은 내가 하지 않는다. **외부 자동 리깅 툴에 넘길 예정**이라 자세 규격 준수가 더 중요하다.
- 자세 스캐폴딩: taxonomy(5클래스)는 Tripo 차용이나, **클래스별 자세 문구는 무출처
  자체 작성으로 판명(2026-08-06)** → 자동 리거 성공률 실험으로 검증 예정(§4·§7).
  실험 전까지 현행 문구 verbatim 유지.
- 내 파트의 LLM 용도: 이미지가 3D로 잘 생성되게 하는 프롬프트 증강 전용.
  생명체 여부 판정과 리깅 타입 판정은 의도 분석 모듈에 요청하기로 이미 결정했다.
- 내 재량 밖: USD 구조(팀 공동 결정), 검색 실패 임계값(검색 모듈 결정).
  이 둘에 대한 변경 제안은 필요 없다.
- rig_type 규약: object xform > etc > rig_type 에 위치.
  값은 biped / quadruped / bird / insect / static_object 5개 중 정확히 1개.
  임의의 값이나 다른 경로를 쓰면 안 된다.
- rig_type의 용도: 리깅은 내가 안 하지만, **나중에 리깅할 수 있는 자세로 생성**해야 한다.
  (사람이면 T포즈로 뽑아야 하는 것과 같은 이유) rig_type이 그 자세를 고른다.
- 주 사용자: 연출·감독. 아티스트가 아니므로 최종 화질이 아니라 판단 가능성이 목적이다.
- 기술 환경: Python 3.10(conda `trellis2`) / TRELLIS.2-4B(image-to-3D) + FLUX.1-schnell(T2I)
  / OpenUSD(pxr) / RTX 4090 24GB ×4 / CLI 배치 실행
- 품질 기준: 사전시각화용이라 최종 렌더 품질보다 형태 인식 가능성·비율 정확도·속도가 우선.
  현재 실측은 객체당 129~386초, 면수 ~95만(과다) — §6 참조
```

## 1. 프로젝트 개요

- **프로젝트명**: 사전시각화 프로젝트
- **사전시각화의 목적**: 본 제작(모델링·촬영·최종 렌더)에 들어가기 전에 장면 구성·인물 동선·
  카메라 워크를 임시 3D로 미리 확인하는 것. 연출 의도를 눈으로 검증해 **수정 비용을
  제작 앞단으로 당기는 것**이 핵심이며, 산출물의 최종 화질은 목적이 아니다.
- **해결하려는 문제**: 프리비즈를 하려면 장면에 놓을 3D 에셋이 있어야 하는데, 검색 DB에
  맞는 에셋이 없으면 아티스트가 직접 모델링해야 한다. 프리비즈는 "빠르게 확인하고 버리는"
  단계라 그만한 시간·비용을 쓰기 어렵고, 그 결과 에셋 확보가 파이프라인 병목이 된다.
  → **검색이 실패한 객체를 자동 생성해 이 공백을 메운다.**
- **최종 목표**: 스토리보드·대본만 넣으면 USD 프리비즈 씬이 자동으로 구성되고, 그 안의
  객체가 검색 또는 생성으로 빠짐없이 채워지는 상태.
  내 모듈 기준으로는 — **검색이 실패한 모든 객체에 대해 리깅 가능한 자세의 3D 에셋을
  자동 생성해 원본 USD에 주입**하고, 하류 모듈이 그대로 쓸 수 있게 만드는 것.
- **기간 / 단계**: **다년 국책과제** 진행 중.
  ⬜ 현재 몇 차년도인지, 이번 연차의 목표 산출물이 무엇인지는 과제 계획서 기준으로 채울 것.
  (이 값이 §6 성능 목표의 기준선이 된다 — 연차 목표가 "시연"이면 속도, "제품화"면
  실패 처리·일관성 쪽이 먼저다.)

## 2. 파이프라인 내 내 위치

전체 흐름:

| 순서 | 모듈 | 담당 |
| --- | --- | --- |
| 1 | 스토리보드·대본에서 사용자 의도 분석 (LLM) | 타 담당자 |
| 2 | 에셋 검색 — DB에 쓸만한 에셋이 있으면 여기서 종료 | 타 담당자 |
| 3 | **3D 객체 생성 (검색 실패 시)** | **본인** |
| 4 | 공간(배경) 생성 — 객체가 놓일 공간을 구성 | 타 담당자 |

⚠️ **실행 순서 확인 필요.** repo의 `run_previs_pipeline.sh`는 `--skip-space`가 t2o보다 앞에
오는 구성이라 **space를 t2o보다 먼저 실행**하는 것처럼 보인다. 위 표(공간 생성이 뒤)와
어긋나므로 담당자와 한 번 맞출 것. 이 순서가 §2 "출력 수신자"와 §6 "실패 시 반환 계약"을
동시에 좌우한다.

- **담당 모듈**: 3D 객체 생성 모듈 (사람을 제외한 사물·생물)
- **하지 않는 일 (경계)**
  - 의도 분석·프롬프트 해석 → 1번 모듈 담당
  - 에셋 검색·중복 판정 → 2번 모듈 담당
  - **사람 에셋** → 별도 담당자. 인체 리깅·변형 토폴로지 제안은 범위 밖
  - 씬 배치, 카메라, 애니메이션, 최종 렌더링 → 후속 모듈
  - USD 구조 변경 → 팀 공동 결정 사항. 개발 중 정말 필요할 때만 회의로 추가·변경
  - 검색 실패 임계값 → 검색 모듈에서 결정
  - **생물의 실제 리깅 작업** → 이 모듈은 리깅하지 않는다.
    리깅 주체: **외부 자동 리깅 툴 사용 예정** (Tripo/UniRig 계열 등). 팀 내 리깅 담당자는 없다.

    ⚠️ **다만 "리깅 가능한 상태로 넘기는 것"은 내 책임이다.** 리깅을 안 한다고 해서
    자세가 자유로운 게 아니다. 사람 에셋을 T포즈로 뽑아야 하듯, 생물도 사지·날개가
    몸통에 붙거나 가려지지 않은 **리깅 친화적 자세**로 생성돼야 한다.
    이것이 `rig_type` → 자세 스캐폴딩 라우팅이 존재하는 이유다(§4).

    ⚠️⚠️ **리거가 사람이 아니라 자동 툴이라는 점 때문에 이 책임이 더 무겁다.**
    사람 리거는 자세가 조금 어긋나도 보고 보정하지만, 자동 리거는 입력 메시가 전제에서
    벗어나면 그대로 실패하거나 잘못된 스켈레톤을 만든다.
    → 자세 스캐폴딩은 "있으면 좋은 것"이 아니라 **하류 성공의 전제 조건**이다.
- **인접 모듈과의 계약**
  - 입력: **USD 파일 자체**가 계약이다. 별도 API·큐 없음. 이 모듈은 루트 USD를 받아
    `customData`를 읽고, 같은 파일 트리에 결과를 되쓴다(in-place 주입).
    읽는 필드 목록과 정확한 prim 경로 → `SNAPSHOT_2026-08-05.md` §1-2, §1-3
  - "검색 실패" 판정: 검색 모듈이 임계값을 정하고 판정한다. 내 모듈은 호출되면 생성한다.
  - 의도 분석 모듈에 요청한 항목: 생명체 여부, 리깅 타입 (→ `rig_type` 필드로 수신)
  - 출력 수신자: **공간(배경) 생성 모듈**(표 4번)이 의도된 소비자다.
    ⚠️ 단 **코드상으로는 확인되지 않았다** — 스냅샷 §5-6 기준, 주입한
    `<defaultPrim>/geometry`를 읽는 하류 코드를 이 서버에서 찾지 못했다.
    위 순서 불일치와 함께 확인 필요.

### 2-1. 검색 모듈 산출물이 USD에 남아 있는 이유

객체 USD에는 `retrieval_result`(koclip 검색의 top-K: `class` / `reference`(usdc) /
`reference_thumbnail` / `score` / `uid`)와 실물 `retrieval_objects/`(약 29MB)가 함께 들어온다.

**이 모듈은 이 값을 읽지 않으며, 그것이 정상이다.** 생성이 호출된 시점은 이미 검색이
실패로 판정된 뒤이므로, `retrieval_result`는 **실패한 검색의 기록**이지 이 모듈의 입력이 아니다.
(실제로 hidden_time/object_1은 rank_1 score 0.2998로 후보는 있었으나 임계값 미달 → 생성으로 넘어왔다.)

관련 상세는 검색 모듈 담당자가 작성 중인 문서를 따른다.
코드상 미소비 사실만 스냅샷 §4-2에 기록돼 있다.

## 3. 사용자와 사용 상황

- **주 사용자**: **연출·감독.** 3D 아티스트가 아니라 연출자가 직접 결과를 보고 판단한다.
  → 산출물은 "아티스트가 다듬을 초안"이 아니라 **"감독이 보고 판단할 수 있는 형태"**여야 하며,
  이것이 §6의 품질 우선순위(형태 인식 가능성 > 디테일)를 정당화하는 근거다.
- **사용 시점**: 스토리보드·대본이 나온 뒤, 본 제작(모델링·촬영)에 착수하기 전.
  파이프라인 안에서는 검색 모듈이 에셋을 찾지 못한 시점에 **자동으로** 호출된다.
  사용자가 이 모듈을 직접 인지하고 부르는 구조가 아니다.
- **1회 사용 시 기대 흐름**
  1. 작품 루트 USD 1개를 CLI로 넘긴다 (`object_generate.sh <루트 USD>`)
  2. 그 안의 scene canonical 객체 전부가 일괄 생성된다 (현재 3객체 = 779초)
  3. 결과가 원본 USD 트리에 in-place 주입된다
  4. 감독이 Blender / USDView로 루트 USD를 열어 장면을 확인한다

  ⚠️ **개별 객체 재생성·수정 인터페이스가 없다.** 특정 객체만 마음에 안 들어도 전체를
  다시 돌려야 한다. 반복 검토가 잦은 프리비즈 성격과 어긋나므로 실사용 전 재검토 대상(§7).
- **실행 단위**: 현재는 작품 루트 USD 1개를 넘기면 **그 안의 scene canonical 객체 전부를
  일괄 배치 처리**한다(shot override는 scene 것을 상속하므로 생성 제외).
  객체 단건 호출 인터페이스는 없다.

## 4. 입출력 명세

- **포맷**: 입력·출력 모두 **USD**. 전체 파이프라인이 USD로 관리되므로 포맷 변환은 논외.
- **USD 규약**: 팀 공동 규약을 따른다. 내가 설계할 대상이 아니며, 준수 대상이다.
  (규약 문서 위치: ⬜ **미확보** — 코드 주석이 "스펙 2.1", "스펙 6절"을 참조하나 그 원문이
  repo 어디에도 없다. 스냅샷 §5-1. → **팀에 원문 위치를 요청할 것.** 이게 없으면 규약
  준수 여부를 스스로 검증할 방법이 없고, 규약 변경도 감지하지 못한다)

### rig_type (리터럴 규약 — 표기를 그대로 지킬 것)

- **경로**: `object xform` > `etc` > `rig_type` ✅ 확정
- **값**: `biped` / `quadruped` / `bird` / `insect` / `static_object` 중 정확히 1개 ✅ 확정
- **판정 주체**: 의도 분석 모듈. 내 모듈은 받은 값을 **읽어서 생성 자세를 고르는 데 쓴다.** ✅ 확정
- `static_object`가 열거값에 있으므로 **무생물 산출물도 이 필드를 비워둘 수 없다**. ✅ 확정
- **기록 의무 없음**: 받은 값을 산출물(USD customData·GLB 메타)에 다시 쓰지 않는다.
  이 모듈에서 rig_type은 **소비되는 입력**이지 전달할 메타데이터가 아니다.
  (원본 USD에 이미 있으므로 하류가 필요하면 거기서 읽으면 된다.)
- 팀 회의로 규약이 바뀌면 이 항목과 압축판을 함께 갱신할 것

**⚠️ `docs/RUN_GUIDE.md:129-141` 은 이 규약을 잘못 적고 있다.**
그 문서는 "customData **최상위** `string rig_type`이 정본이고 `etc` 중첩은 구 스펙"이라고
서술하나, **팀 합의 정본은 위의 `etc > rig_type`이다.** `usd_parser.py:151` 주석도 같은 오류를
담고 있다. 다만 코드 `_resolve_rig_type()`(`usd_parser.py:149-179`)이 ①최상위 → ②`etc` 중첩 dict
→ ③자식 prim `etc` 를 **모두 읽으므로 동작에는 문제가 없다.** 문서·주석 수정 과제다
(스냅샷 §3-10).

### rig_type의 진짜 용도 — 리깅 가능한 자세로 생성하기

이 모듈은 리깅을 하지 않는다. 그러나 **나중에 리깅할 수 있는 자세로 메시를 뽑아야 한다.**
사람 에셋을 T포즈로 생성하는 것과 같은 이유다 — 사지가 몸통에 붙거나 서로 가려진 채로
생성되면 그 메시는 리깅할 수 없다.

`rig_type`은 그 자세를 고르는 스위치다. 값에 따라 **고정 자세 문구(스캐폴딩)** 가
T2I 프롬프트에 verbatim 삽입된다(`t2i_prompt_builder.py:31-51`):

| rig_type | 강제 자세 (요지) |
| --- | --- |
| `biped` | **A-pose**, 팔을 몸에서 약간 벌려 내림, 다리 곧게 약간 벌림, 정면 |
| `quadruped` | 네 다리로 자연 기립, **네 다리가 모두 분리·신전**, 접지 않음, 측면 |
| `bird` | **날개를 좌우 대칭으로 완전히 펼침**, 기립, 정면 |
| `insect` | **여섯 다리가 모두 분리·신전**, 기립, 측면 |
| `static_object` | 자세 강제 없음 (격리 문구만) |

**자세 문구의 출처 — 2026-08-06 재조사로 정정**

기존 서술("기존 리깅 프로젝트의 rig-type 규약을 그대로 참조했으므로 자체 검증 안 함")은
**절반만 사실**이었다. 재조사 결과:

- **taxonomy(클래스 분류)는 실제 차용이다.** Tripo API에 rig 타입 열거가 실존한다
  (biped / quadruped / hexapod / octopod / avian / serpentine / aquatic).
  → taxonomy에 대한 "검증 불필요" 판정은 **유지**.
- **클래스별 자세 문구는 차용이 아니다.** Tripo·UniRig 어디에도 클래스별 자세 명세가
  문서화돼 있지 않다. 업계에 문서화된 자세 요구는 **humanoid에 한정**되며 그마저 툴마다
  다르다(Mixamo=T포즈 요구, AccuRig=A포즈+정면 요구, Tripo=명시 없음).
  비인간 클래스(quadruped/bird/insect)의 자세 요구를 문서화한 툴은 **찾지 못했다.**
  → 자세 문구는 업계 관행에서 외삽한 **무출처 자체 작성**으로 판정. **검증 대상으로 재개방.**
- **검증 방법**: 사람 O/X 채점(`SERVER_4090_SETUP.md:197-213`의 구 제안)이 아니라
  **자동 리거 성공률 실험** — 스캐폴딩 on/off × 클래스 × 시드로 생성한 메시를
  자동 리거(UniRig 로컬 / Tripo rig-check)에 넣어 성공률을 잰다. §7 등록.
- 결과적으로 `SERVER_4090_SETUP.md`의 "잠정값, 검증 안 됨" 서술이 **옳았고**,
  2026-08-05의 스테일 판정(스냅샷 §3-11)이 성급했다. "검증 문구 걷어내기" 과제는 취소.
- 실험 전까지는 현행 문구를 verbatim 유지한다(무근거 변조가 더 나쁘다).

taxonomy 차용의 근거로 유효하게 남는 참조 주석:

- `t2i_prompt_builder.py:12-14` — `Tripo/UniRig 의 rig-type taxonomy(biped/quadruped/bird/…)를
  참고하되, 저쪽은 3D 메시 지오메트리로 판정한다(post-mesh). 우리는 메시가 없는 text→image
  단계라 그 방식을 그대로 쓸 수 없어서, USD category + 객체명(en) 키워드 dict 로 결정론적 분류한다.`
- `docs/SERVER_4090_SETUP.md:208` — `자세 기준은 후속 리깅 요구에서 나왔다(Tripo rig-type 참고
  — 실제 리거로 Tripo 를 쓰는 건 아님).`

**⚠️ 단 `SERVER_4090_SETUP.md:208`의 "실제 리거로 Tripo를 쓰는 건 아님"은 재확인 대상이 됐다.**
리깅 주체가 **외부 자동 리깅 툴**로 정해졌으므로(§2·§9), 실제로 어떤 툴을 쓰느냐에 따라
저 문장이 사실과 달라질 수 있다. 툴 선정 시 이 서술과 아래 A포즈 항목을 함께 갱신할 것.

**남은 주의 2가지**

1. **`biped`는 T포즈가 아니라 A포즈로 고정돼 있다**(`t2i_prompt_builder.py:32-36`).
   ⬜ **확인 필요** — 다만 판단 기준은 명확해졌다. 리거가 사람이 아니라 **자동 툴**이므로
   기준은 "사람이 리깅하기 편한가"가 아니라 **"우리가 쓸 자동 리거가 어느 자세를 전제하는가"**다.
   2026-08-06 조사에서 이 요구가 **툴 종속**임이 확인됐다(Mixamo=T포즈, AccuRig=A포즈).
   → **리깅 툴 선정과 동시에 확정할 것.** 툴이 정해지기 전에는 이 항목을 열어둔다.
   (이 모듈의 biped 대상은 사람이 아니라 고릴라·원숭이·로봇·캥거루 등이다.)
2. **`insect` 클래스의 처지가 역전됐다(2026-08-06).** 종전에는 "참조 원안에 없던 신규
   클래스라 리거가 곤충을 지원하지 않으면 클래스 재검토" 대상이었으나, 현행 Tripo v2.5가
   **hexapod를 명시 지원**함을 확인 → **클래스 존치 근거는 확보됐다.**
   무출처로 남는 것은 클래스가 아니라 **자세 문구**다(위 정정 참조).

### rig_type enum ↔ 리거 taxonomy 대응 (2026-08-06 조사)

프로젝트 enum 5개는 의도분석 모듈 담당자와 합의된 **팀 계약**이다(확장·변경은 회의 안건).
현행 자동 리거들의 taxonomy와 대조:

| 프로젝트 enum | Tripo v2.5 rig 타입 | 비고 |
| --- | --- | --- |
| `biped` | biped | 일치 |
| `quadruped` | quadruped | 일치 |
| `bird` | avian | **명칭 불일치** — 리거 연동 시 매핑 필요 |
| `insect` | hexapod | **명칭 불일치** — 리거 연동 시 매핑 필요 |
| `static_object` | (없음) | 프로젝트 자체 발명("리깅 없음" 마커) — 리거 taxonomy에 없는 것이 정상 |
| (없음) | serpentine / aquatic / octopod | ⬜ **커버리지 공백** — 뱀·어류·문어류가 대본에 나오면 분류 불가. 5클래스 충분성을 의도분석 담당자와 확인할 것 |

**타 리거 taxonomy 조사 (2026-08-06, 리깅 툴 선정 참고용)**

| 리거 | taxonomy | 문서화된 자세 요구 |
| --- | --- | --- |
| Tripo v2.5 (API) | biped/quadruped/hexapod/octopod/avian/serpentine/aquatic — 7종 | 없음 (rig-check 사전 판정 API 존재) |
| UniRig (오픈소스, SIGGRAPH 2025) | **taxonomy-free** — 고정 클래스 없이 스켈레톤 트리를 autoregressive 생성 | 없음 |
| Anything World | 카테고리 기반: humanoid / quadruped(canine·feline 세분) / vehicle / static | 방향(facing)·대칭만 명시 |
| Meshy | 사실상 humanoid 중심 | 없음 |
| AccuRig (Reallusion) | humanoid 전용 | **A포즈 + 정면** 요구 |
| Mixamo (Adobe) | humanoid 전용 | **T포즈** 요구 |

시사점: 클래스 enum이 리거 입력으로 의미 있는 것은 **템플릿 기반 리거(Tripo 계열)뿐**이다.
taxonomy-free 리거(UniRig)를 선정하면 enum은 리거 입력이 아니라 **생성 자세 선택 전용**으로
남는다(현재 용도와 일치, 규약 변경 불필요). 비인간 자세 요구는 어느 리거도 문서화하지
않았으므로, 어떤 툴을 고르든 **자세 문구의 근거는 우리 실험이 만들어야 한다**(§7).

### 참고 입력 — `image_path` (의무 아님, 현재 미사용)

- **정체**: 최초 입력인 **스토리보드에서 잘라낸 원본 이미지**. 대부분 스케치 또는
  그보다 조악한 선 그림이고, **자동 인식으로 잘라내므로 인식 실패가 있다.**
- **성격**: 의무 필드가 아니다. 다른 모듈이나 이 모듈이 참고할 수 있으면 쓰라고
  전달하는 **best-effort 값**이다. (실측 채움률 3건 중 1건 — 정상)
- **현재 처리**: 파서는 읽지만 하류로 넘기지 않는다(스냅샷 §4-3).
  초기에 사용을 시도했으나 **품질이 오히려 떨어져 현재는 쓰지 않는다.**
  향후 활용 가능성이 있어 **명시적으로 제거하지도 않는다.** → **현 상태 유지가 의도된 결정.**
- **왜 품질이 떨어지는가**: TRELLIS.2는 이미지 조건부 모델이라 입력 이미지의 형상이
  그대로 3D로 전이된다. 이 모듈의 T2I 프롬프트는 격리·정면·전신의 깨끗한 참조 이미지를
  만들도록 설계돼 있는데, 선 그림 크롭은 자세·완결성·표면 정보가 그 기준에 못 미친다.
- **되살린다면**: "쓴다/안 쓴다"가 아니라 **품질 게이트 통과 시에만 T2I를 건너뛰는
  조건부 경로**가 되어야 한다. 유사 구현이 `prompt_lab/previs_lab/pipeline.py:178`
  `lift_only()`에 이미 있다(별도 실험 도구).

## 5. 기술 환경

- **언어·프레임워크**: Python 3.10 (conda env `trellis2`)
- **생성 모델 / 알고리즘**:
  - **TRELLIS.2-4B** — image-to-3D 본체. 텍스트 입력을 받지 않으므로 중간 이미지가 필수
  - **FLUX.1-schnell** — text-to-image. Apache-2.0이라 상업적 사용 제약 없음(dev는 비상업)
  - 파이프라인: 프롬프트 → FLUX → 이미지 → TRELLIS.2 → 메시 → GLB → USD
- **USD 처리 라이브러리**: OpenUSD Python API (`pxr`, `usd-core 25.8`).
  GLB 파싱은 `trimesh`. GLB→USD 변환기는 자체 구현(`glb_to_usd_native.py`) —
  구 `usd_from_gltf` 바이너리를 대체해 외부 의존 0
- **DCC·엔진 연동**: **Blender / USDView에서 원본 USD를 그대로 열면 보이는 것**이 목표이며
  현재 충족된다(README). 루트·scene·shot·object 어느 레벨을 열어도 주입된 geometry가
  텍스처와 함께 로딩된다. 게임엔진(Unreal/Unity) 연동 요구는 확인된 바 없다 —
  요구가 생기면 좌표·단위 규약(§4)과 폴리곤 예산을 함께 재검토해야 한다.
- **실행 환경**: RTX 4090 24GB × 4. 핀 고정 필수 —
  `transformers==4.56.2`, `opencv-python-headless==4.11.0.86`, `torch 2.6.0+cu124`,
  `diffusers 0.39.0`. CUDA 확장(o_voxel/flex_gemm/cumesh/flash_attn)은 sm_89로 빌드됨
- **실행 형태**: CLI 배치. `object_generate.sh <루트 USD> [--no-filter] [-- <추가인자>]`
  ⚠️ 이 런처는 **repo 밖**(`previs_proj/` 최상위)에 있어 git 추적되지 않는다(스냅샷 §5-4)
- **GPU 배치 제약**: FLUX와 TRELLIS.2를 같은 24GB 카드에 올리면 OOM.
  `T2I_GPU`로 다른 카드에 분리해야 한다

## 6. 제약과 품질 기준

- **성능 목표**: ⬜ **미정.** 다만 기준의 *성격*은 정해진다 — 주 사용자가 연출·감독이고
  실행 단위가 작품 단위 일괄 배치이므로(§3), 의미 있는 단위는 "객체당 몇 초"가 아니라
  **"작품 한 편이 하룻밤 안에 끝나는가"**다. 구체 수치는 과제 연차 목표(§1)가 정해져야 확정된다.

  **현재 실측** (2026-08-05, 객체 3개 전체 실행 = 779초):

  | 구간 | 시간 | 비중 |
  | --- | ---: | ---: |
  | save (`to_glb`: remesh+decimation+텍스처 베이크) | 345.7s | 44% |
  | T2I (FLUX) | 124.3s | 16% |
  | 프리뷰 렌더 | 122.5s | 16% |
  | I2O (TRELLIS.2) | 81.3s | 10% |
  | TRELLIS.2 모델 로드 | 78.6s | 10% (1회) |

  객체당 129~386초로 편차가 크다(같은 객체도 시드에 따라 24s↔272s).
  **참고 환산**: 모델 로드 1회를 빼면 객체당 약 233초 → 객체 100개짜리 작품이면 약 **6.5시간**.
  야간 배치로는 되지만 당일 반복 검토에는 부족하다.
  개선안과 실험 절차는 `PERF_EXPERIMENTS.md`.

- **품질 우선순위**: 사전시각화용이므로 **형태 인식 가능성·비율 정확도·속도 > 디테일·텍스처 품질**.
  주 사용자가 아티스트가 아니라 연출·감독이라는 점이 이 우선순위의 근거다(§3).
  이 전제가 §4의 폴리곤 예산 하향(1M → ?)을 정당화한다.
- **리깅 가능성**: 위 우선순위와 별개로 **생물은 리깅 가능한 자세로 나와야 한다**(§4).
  자세 taxonomy는 Tripo 차용이나, **클래스별 자세 문구는 무출처 자체 작성으로 판명됐다**
  (2026-08-06, §4) → **자동 리거 성공률 실험으로 검증 예정**(§7). 실험 전까지는 현행
  문구를 verbatim 유지한다. 리거가 자동 툴이므로, **툴 선정 후에는 그 툴의 입력
  요구사항이 실질적 검증 기준이 된다.**
- **검색 결과와의 일관성**: ⬜ **미정.** (생성 에셋이 기존 DB 에셋과 스타일·스케일 규약에서
  어긋나지 않아야 하는가. 스케일은 `metersPerUnit=0.01`·×100 규약이 있으나
  검색 DB 에셋이 같은 규약인지 확인 안 됨)
  → 한 씬에 **검색 에셋과 생성 에셋이 섞여 놓이는** 구조이므로, 스케일 규약 불일치는
  감독이 즉시 알아채는 종류의 오류다. 검색 모듈 담당자와 우선 확인할 것.
- **실패 허용 범위**: ⬜ 재시도 정책 없음. 현재 코드는 객체별로 예외를 잡아 기록하고
  다음 객체로 넘어간다. 일괄 배치 구조상 "일부 실패해도 나머지는 진행"은 타당하다.
  다만 **생성마저 실패했을 때 무엇을 반환하는가가 미정** — 현재는 geometry 참조가 주입되지
  않은 채 원본 USD가 남는다. 하류(공간 생성 모듈)가 이 "빈 객체"를 어떻게 다뤄야 하는지,
  그리고 감독에게 실패 사실이 어떻게 보이는지가 정의되지 않았다.
- **라이선스·데이터 제약**: FLUX.1-schnell = Apache-2.0(상업 사용 가능).
  **FLUX.1-dev는 비상업 라이선스라 제품에 넣으면 안 된다** — 진단 용도로만 사용.
  → 국책과제 산출물이라 **상업 사용 가능성을 열어두는 쪽이 안전**하다. schnell 고정 유지.
  (같은 이유로 **FLUX.1 Kontext [dev]도 비상업** — 참조 이미지 편집 경로를 추가할 때
  Kontext dev는 후보에서 제외. 오픈 가중치 대안: Qwen-Image 계열(Apache-2.0) 등. 2026-08-06)

> 근거를 함께 적어두면, 나중에 전제가 바뀌었을 때 결정을 다시 열어야 할 시점을 알 수 있다.

**⚠️ 전제가 흔들리는 결정 (3건)**

1. **"생명체 여부·리깅 타입 판정 위임"** — 확정이나, `rig_type`이 실제로 도착하기 전까지는
   코드가 **자체 키워드 분류**로 돌고 있다(§7). 위임이 실현되면 `t2i_prompt_builder.py`의
   키워드 dict는 폴백으로만 남아야 한다.
2. **"`rig_type`은 산출물에 기록하지 않는다"** — 근거는 "원본 USD에 이미 있으므로 하류가
   거기서 읽으면 된다"였다. 그런데 리거가 **외부 자동 툴**로 정해졌으므로, 그 툴이 USD가
   아니라 **GLB만 받는 경우** 이 근거가 성립하지 않는다(GLB에는 rig_type이 없다).
   → 리깅 툴 선정 시 "입력으로 무엇을 받는가"를 먼저 확인하고, GLB 단독이면 이 결정을 다시 열 것.
3. **"자세 스캐폴딩 = 차용 규약 → 자체 검증 안 함"** — 2026-08-06 재조사로 이 근거가
   **taxonomy에만 성립**함이 확인됐다(§4). 자세 문구는 무출처 자체 작성 → 위 표에서 결정의
   범위를 taxonomy로 축소하고, 문구 검증(자동 리거 성공률 실험)을 §7에 등록했다.
   실험 전까지 현행 문구는 verbatim 유지(무근거 변조가 더 나쁘다).
