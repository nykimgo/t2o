### 3-1. `rig_type` 정규화가 두 곳에 중복 구현되어 있고 별칭 집합이 다르다

| 위치 | 별칭 집합 |
|---|---|
| `usd_parser.py:144` | `{"static", "staticobject", "inanimate", "prop", "object"}` |
| `t2i_prompt_builder.py:63` | `{"static", "staticobject", "inanimate", "non_creature", "object", "prop"}` |

참고로 품질 저하는 구조적으로 설명된다: `text_to_image.py` 와 `t2i_prompt_builder` 의 스캐폴딩은
**격리·정면·전신의 깨끗한 참조 이미지**를 만들도록 설계돼 있는데(§1-6), 스토리보드 선 그림 크롭은
자세·완결성·표면 정보가 그 기준에 못 미친다. TRELLIS.2 는 이미지 조건부 모델이라(`trellis2_inference_core.py:232`)
입력 이미지의 형상이 그대로 3D 로 전이된다.

→ **설계 논의 시사점**: 이 필드를 되살리려면 "쓰느냐 마느냐"가 아니라
**품질 게이트를 통과한 경우에만 T2I 를 건너뛰는 조건부 경로**가 되어야 한다.
유사 구현이 이미 존재한다 — `prompt_lab/previs_lab/pipeline.py:178` `lift_only()`
("기존 이미지 재사용(생성 안 함)", CV 검사 후 리프트만 수행). 단 이는 **별도 실험 도구**이며 본 파이프라인 코드가 아니다.

### 4-4. `appearance`가 생명체 경로에서 소실된다

`_creature_prompt`(`t2i_prompt_builder.py:168-183`)는 `appearance`를 받지 않는다.
`usd_parse_and_augment.py:648-650`은 `appearance`를 essential에 복사하며 "§9 무생물 템플릿의 `{appearance}` 슬롯 입력"이라고 명시한다.
즉 **의도된 설계**이나, 업스트림이 생명체의 샷별 외형을 `appearance`로 보내면 **그 정보는 반영되지 않는다.**

### 4-5. `base_description` vs `description` 스키마 혼재

`usd_parser.py:186-192`가 `description → base_description → appearance` 폴백으로 신·구 스키마를 동시에 받는다.
어느 쪽이 정본인지 문서가 갈린다: `README.md:93`은 `base_description`을 `dictionary {ko,en}`으로,
`docs/RUN_GUIDE.md:104-105`는 `string base_description = "..."` 플랫 문자열로 적는다.
코드는 둘 다 처리하므로 **현재는 무증상이지만, 업스트림 계약으로는 미확정**이다.

### 4-6. 카메라 USD의 customData 위치 오류 (미수정)

`docs/SERVER_4090_SETUP.md:160-162`:
`카메라 USD 10개가 파싱 실패 — customData 가 레이어 메타데이터 블록에 들어가 있다. USD 는 거기서 customData 를 허용하지 않는다(customLayerData 만) … object 생성엔 무해하나 렌더/카메라 사용 시 터진다. **미수정.**`

2026-08-05 실행 로그에서도 동일 경고가 shot_1~10 전부에서 재현된다
(`Could not open asset … camera_1.usda … Expected ) at 'customData = {'`). 업스트림 산출물의 스키마 위반이며 이 모듈 밖 문제다.

### 5-1. 코드가 참조하는 "스펙"의 원문이 repo에 없다

### 5-2. `§9` 프롬프트 규약은 이 repo 밖에 있다

`t2i_prompt_builder.py:1`이 근거로 드는 `prompt_lab EXPERIMENT_LOG.md`의 실제 위치는
`/home/sr/previs_proj/prompt_lab/docs/EXPERIMENT_LOG.md`로, **t2o_pipeline repo 외부**다(경로 표기도 코드 주석과 다름).
`docs/SERVER_4090_SETUP.md:182`는 "repo 안에 남은 유일한 T2I 템플릿 근거"라고 하나, §3-2처럼 코드와 어긋난다.

### 5-3. 문서의 검증 주장을 로컬 데이터로 재현할 수 없다

`docs/RUN_GUIDE.md:139-141`은 `hidden_time / welcom2dmk / berlin` 3작품으로 rig_type을 검증했다고 하나,
이 서버 `movie_usd/`에는 **`hidden_time` 하나뿐**이다. 나머지 2작품 산출물은 확인 불가.
또 `docs/RUN_GUIDE.md:93-95`는 `base_description`/`appearance`가 비어 있다고 하나 로컬 `object_1.usda`는 채워져 있다
— 해당 문서가 A100/도커 서버 기준이라 이 서버에 그대로 적용되지 않는다.

두 경우 모두 **서버 왕복 과정에서 데이터·문서가 서버별로 갈라진 결과**로 보인다(§헤더). [담당자 확인]
따라서 이 항목들은 "문서가 틀렸다"가 아니라 **"이 서버에서는 재현할 수 없다"** 로 읽어야 한다.

같은 이유로 §4-1 의 rig_type 수동 주입 테스트도 산출물이 로컬에 없어 재현 확인이 불가하다.
→ 설계 논의가 rig_type 경로에 의존한다면, **테스트용 USD 픽스처를 repo 에 남기는 것**이 이 공백을 없애는 가장 싼 방법이다.

### 5-4. 런처가 버전 관리 밖이라 이력 대조 불가

`object_generate.sh`(26,033바이트, mtime 2026-07-23)는 repo 밖이라 git 이력이 없다.
CLI 계약이 언제 어떻게 바뀌었는지 추적할 수 없다.

### 5-5. 필터/번역 경로의 실제 산출 형태 미확인

`--filter` 실행 이력이 0건이라(§2-2) `t2i_prompt`가 "정제 캡션"으로 채워졌을 때의 실제 문자열,
그리고 그때 `appearance`가 빠지는 분기(`usd_parse_and_augment.py:942-946`)의 동작을 관측한 적이 없다.
ollama는 이 서버에서 응답하므로 **실행은 가능하나 미실행** 상태다.

### 5-6. 다운스트림 소비자를 확인하지 못했다

이 모듈이 주입한 `<defaultPrim>/geometry`를 실제로 읽는 하류 모듈(렌더/합성)의 코드는 이 조사 범위에서 발견하지 못했다.
