# 기술이전용 자원 대응 파이프라인 구현 계획

작성: 2026-09-10. 선행 분석: `MAIN_PIPELINE_SPEED_AUDIT_20260909.md`.
이 문서는 구현 계획이며, 현재 코드의 지원 보증이나 완료 보고가 아니다.

## 1. 목표와 기본 결정

- **RTX 4090 24GB 한 장**에서 USD 입력 → 정제 → ERNIE → TRELLIS.2 → GLB → USD 연결까지 실행되는 경로를 기본 제품으로 만든다.
- 2 GPU는 같은 생성 기능의 처리량 확장이다. 모델·입력·출력 품질 설정을 GPU 수에 따라 자동 변경하지 않는다.
- 현재 서버의 4 GPU, 128GB급 RAM, 특정 물리 GPU 번호에 의존하지 않는다. 초기 자동 병렬화는 최대 2 GPU까지만 검증·지원한다. 4 GPU 확장은 후속이다.
- VRAM 24GB 미만, 다른 GPU 종류, 최소 시스템 RAM은 아직 보장하지 않는다. 실제 측정으로 지원표를 확정한다. 한 장이라는 이유만으로 모든 GPU를 지원한다고 표시하지 않는다.
- Linux 생성 서버 + 내부망 Windows 브라우저가 1차 배포 형태다. Windows 네이티브 생성 서버는 별도 지원 범위다.
- ERNIE 기본, 자동 보강 ON, 3/4뷰·리깅 포즈를 유지한다. Qwen INT8은 자원이 충족되는 환경에서 선택 가능하게 한다.
- 메인 자동 생성은 기본적으로 객체당 참조 이미지 1개를 사용한다. UI의 후보 2~4개 생성과 구분하며, 후보 4개를 요청했다고 GPU에서 반드시 4개를 동시에 처리하지 않는다.
- 기술이전 준비와 CLIP/FID 연구 평가를 분리한다. 실행 설정·계측 기록은 공유할 수 있으나 평가 목표 달성이 인도 차단 조건은 아니다.

## 2. 구조: UI와 CLI가 공통 실행 계층 사용

공통 흐름:

`입력 검증 → 외형 정제 → T2I 보강/인코딩/생성 → 전처리 → 3D conditioning/형상/재질 → GLB 후처리 → USD 연결`

- UI와 기존 CLI를 입력 어댑터로 두고 모델 호출, 자원 배정, 작업 상태, checkpoint, 시간 기록을 공통 실행 패키지로 옮긴다.
- 기존 UI의 SQLite 기록·이미지별 version ID·batch ID·조회 URL을 유지한다. 새 필드를 추가하는 방식으로 호환하고, 예전 기록에 없는 시간은 추정해서 채우지 않는다.
- 같은 데이터 루트에는 실행 조정자가 하나만 존재하도록 잠근다. UI와 CLI는 같은 작업 큐에 제출한다. 서비스가 없는 CLI 실행은 같은 엔진을 시작해서 사용하며, 별도 GPU 실행 경로를 만들지 않는다.
- 단일 호스트의 GPU별 실행 잠금은 공통 엔진을 통하는 모든 worker가 공유한다. 별도 프로그램까지 통제한다고 가정하지 않고 실제 외부 점유를 계속 확인한다.
- 현재 `generation_ui`가 실험 폴더의 Qwen loader를 직접 가져오는 의존성을 공통 모델 어댑터로 옮긴다. 모델 경로·가중치 revision·생성 설정을 한 곳에서 관리한다.
- 처음부터 메인 전체를 교체하지 않는다. 현재 경로를 기준선으로 보존하고 새 엔진을 선택하는 설정을 거쳐 단계적으로 전환한다.

## 3. 자원 인식과 실행 허가

설치/시작 시 다음을 수집한다.

- 허용된 GPU 목록, UUID, 논리 장치 매핑, VRAM 총량·여유량, 드라이버·CUDA 호환성.
- CPU 수, 사용 가능한 시스템 RAM, 디스크 여유·작업 폴더 쓰기 가능 여부.
- 모델·환경 manifest와 로컬 파일 존재 여부.
- 모델/단계/해상도/동시 처리 수별로 검증된 최대 메모리와 실행 시간 프로필.

정책:

1. 관리자 지정 GPU 목록과 `CUDA_VISIBLE_DEVICES`를 우선한다. 기본은 허용된 장치 중 한 장만 사용한다. 두 장 사용은 설치 설정에서 명시한다. 다른 작업 때문에 바쁜 GPU를 강제로 비우지 않는다.
2. 물리 GPU `1` 하드코딩을 제거한다. 할당받은 GPU만 worker에 노출하고 worker 내부에서는 논리 `cuda:0`을 사용한다.
3. 현재의 모든 작업 공통 `22000MiB 여유` 조건을 단계별 요구량 + 안전 여유로 대체한다. 현재 여유 VRAM뿐 아니라 CPU RAM도 충족해야 실행한다.
4. 안전 여유는 초기에는 GPU별 `max(1GiB, 총 VRAM의 5%)`, 시스템 RAM은 `max(8GiB, 사용 가능한 메모리 한도의 15%)`를 예약하는 정책으로 시작한다. 이는 최소 지원 사양이 아니라 scheduler의 보수적인 여유 정책이다. 실제 피크 변동을 측정해 프로필을 보정한다.
5. PyTorch reserved 수치만으로 실행을 허가하지 않는다. NVML의 전체 장치/프로세스 점유와 프로세스 트리의 CPU RSS를 함께 사용한다. 프로세스 밖 CUDA 할당도 포함한다.
6. 미측정 조합은 가장 보수적인 검증 경로에서 시작한다. 지원 프로필이 없거나 필수 메모리 요구량을 판단할 수 없으면 미검증 상태를 표시하고 진단·검증 절차를 거치게 한다.
7. 일시적인 외부 점유는 대기 상태와 이유를 표시한다. 총 사양 자체가 부족한 경우에는 무한 대기 대신 지원 불가 사유를 반환한다. GPU가 없으면 기존 결과 조회·다운로드는 가능하고 생성은 비활성화한다.
8. 같은 모델명이어도 GPU·드라이버·패키지 버전·정밀도·해상도·가중치·코드 revision이 바뀌면 기존 속도/메모리 프로필을 무조건 신뢰하지 않는다.

## 4. GPU 수·RAM에 따른 실행 정책

| 환경 | 실행 정책 | 모델 재사용 정책 |
|---|---|---|
| 1 GPU, 보수적 경로 | GPU를 쓰는 정제/T2I/전처리/3D/GLB 단계를 순서대로 실행 | 같은 단계의 연속 작업에서 재사용. 다음 대형 모델을 올리기 전 GPU 메모리 반환 확인 |
| 1 GPU, 충분한 RAM이 검증된 환경 | 동일한 GPU 직렬 실행 유지 | 비활성 모델을 CPU에 보관하는 방식과 worker 종료 방식을 비교해 검증된 쪽 사용 |
| 2 GPU, 충분한 RAM | GPU A는 다음 객체의 T2I, GPU B는 현재 객체의 I2O+GPU 후처리 | 서로 다른 worker가 담당. CPU UV·변환 부하까지 합쳐 동시 실행 허가 |
| 2 GPU이나 RAM 부족/한 장 외부 점유 | 신규 작업부터 1 GPU 정책으로 실행 | 실행 중인 정상 작업을 강제로 이동시키지 않고 완료 checkpoint 경계에서 전환 |

세부 결정:

- 기본 작업 순서는 **첫 결과 우선**이다. 첫 객체를 끝까지 처리한 뒤 후속 객체에서 모델 전환 비용을 줄이는 소량 묶음을 적용한다. 대규모 USD 요청에는 별도 처리량 우선 모드를 제공한다.
- 처리량 우선 모드는 참조 이미지들을 묶어 만들고 3D 모델을 재사용한다. 모든 참조 이미지를 먼저 생성하면 첫 3D 결과가 늦어질 수 있음을 기록한다.
- 준비된 후속 객체는 기본 최대 2개만 앞서 생성해 checkpoint로 둔다. CPU 변환 worker 기본값은 1개이며 측정 후 확장한다. 큐가 GPU·RAM·디스크를 무제한 점유하지 않도록 한다.
- T2I 후보 출력 수와 GPU 실행 batch 크기는 독립 변수다. 같은 객체의 후보들은 보강을 한 번 공유하지만 서로 다른 객체는 각각 보강한다.
- 한 GPU에서 T2I와 TRELLIS.2를 동시에 실행하지 않는다. GPU를 쓰는 GLB 후처리도 이 제약에 포함한다. LLM을 GPU에서 실행한다면 정제 단계 역시 GPU 사용권을 얻고 반환한다.
- CPU LLM도 무료 자원이 아니다. RAM이 부족하면 T2I/3D 모델과 동시에 CPU에 유지하지 않는다. 원격 LLM은 기존에 구성한 경우에만 사용하며 자동으로 외부 서비스에 전송하지 않는다.
- GPU 사용권 반환은 단순 `empty_cache()` 호출을 기준으로 삼지 않는다. 살아 있는 tensor·offload hook·CUDA context의 점유를 확인한다. 검증되지 않은 모델 상주 방식에서는 worker 종료를 확실한 반환 경계로 사용한다.
- CPU 상주 재사용은 필수 요건이 아닌 최적화다. 누수·RAM 증가가 있으면 재사용을 해제한다. RAM을 swap으로 밀어 넣어 명목상 동시 실행하는 정책은 사용하지 않는다.
- 리깅과 부분편집은 1차 생성 scheduler의 자동 동시 실행 대상에 추가하지 않는다. 이후 공통 자원 예약에 참여시키되, 기존 RAM 제약을 따로 검증한다.

## 5. 품질 설정과 실행 설정 분리

품질 설정: 모델·가중치, 정제/보강 규칙, 원문/보강문, 각 seed, 해상도, sampler, mesh 해상도, remesh, 면 수, 텍스처 크기.

실행 설정: 허용 GPU, 동시 worker 수, 후보 처리 batch 크기, CPU offload, 모델 유지/종료, 큐 순서, CPU thread 수.

- `환경 자동 설정`은 실행 설정만 조정한다. 품질 설정을 낮추거나 Qwen을 ERNIE로 몰래 바꾸지 않는다.
- 공통 품질 프리셋을 정의하되 기존 입력의 명시적 설정을 우선한다. 기존 CLI 1024 텍스처와 UI 2048 텍스처는 각각 이름을 가진 호환 프리셋으로 보존한다. 비교·인도 스펙에서는 사용할 프리셋을 반드시 명시한다.
- 인도용 품질 프리셋의 우선 검증 대상은 현재 UI의 1024_cascade·목표 100만 면·2048 텍스처다. 실측 전에 다른 기본값으로 자동 통일하지 않는다.
- 메모리가 부족하면 batch 축소 → 비활성 모델 해제/offload → 안전한 worker 재시작 순으로 대응한다. 그래도 실패하면 사유와 마지막 완료 결과를 남긴다.
- 면 수·텍스처·sampling 축소는 사용자가 별도 품질 프리셋을 선택한 경우만 허용한다.

## 6. checkpoint·재시도·원본 보존

checkpoint 단위:

1. 정제 결과와 사용한 규칙/모델 정보.
2. 객체별 보강문·보강 seed 및 후보별 diffusion seed.
3. 참조 이미지·전처리 이미지.
4. 재시도에서 재사용할 이미지 conditioning.
5. mesh와 재질 속성 volume.
6. 정리된 mesh·UV atlas.
7. GLB와 USD 변환 결과.

- 각 출력은 임시 파일로 쓰고 검증 후 원자적으로 완료 표시한다. 중간에 생긴 파일만으로 성공 처리하지 않는다.
- cache key는 해당 단계의 입력 hash와 계산에 영향을 주는 버전을 포함한다. category나 객체 이름만으로 재사용하지 않는다.
- CPU/GPU tensor cache는 다른 worker에서도 불러올 수 있는 내부 형식으로 저장한다. 외부 업로드 파일을 임의 pickle로 로딩하지 않는다. 디스크 cache는 용량 제한·최근 사용 정책을 적용하며 원본과 확정 결과는 자동 삭제하지 않는다.
- 재시도는 같은 조건에서 미완료 단계만 실행한다. '새로 생성'은 새로운 시도를 만든다.
- 깊이붕괴 재시도에서는 mesh·참조 이미지·각 seed를 한 시도 묶음으로 저장한다. 여러 시도 중 최선의 mesh를 선택할 때 대응하는 이미지도 함께 선택한다.
- CUDA OOM은 batch 축소로 제한 재시도한다. 4→2→1 축소와 단일 처리의 깨끗한 worker 재시작 1회까지만 허용한다. 무한 루프나 일반 오류의 무조건 자동 재실행을 금지한다.
- 중지는 해당 작업이 소유한 worker만 종료한다. 완료된 후보·mesh는 보존한다. 서비스 재시작 시 실행 중 작업은 중단 상태로 복구하고 GPU 사용권은 생존 프로세스 확인 후 정리한다.
- USD 변환은 서로 다른 객체의 독립 출력만 겹쳐 실행한다. 동일 레이어에 대한 수정·원본 주입은 직렬화한다. 실패 시 기존 참조를 유지한다.

## 7. 최적화 순서

### 0단계 — 기준선과 호출 계약 정리

- 루트 `object_generate.sh`의 `--backend`와 현재 argparse 불일치 해결. 현행 TRELLIS.2만 지원하는 계약으로 일치시키고 이전 v1 안내를 정리한다.
- 장치 번호·모델 경로·프리셋·실행 설정을 수집하고 실행 manifest에 기록한다.
- 전체 시간, 실패/재시도 시간, GPU별 메모리, CPU 메모리를 계측한다. cold/warm, UI/CLI 프리셋 차이를 구분한다.
- 이 단계는 실제 생성 알고리즘을 바꾸지 않는다.

### 1단계 — 단일 GPU 공통 엔진과 복구

- 현재 UI에서 검증한 단계 분리·후보 batch·중지/재시도 로직을 공통 계층으로 이동한다.
- GPU 번호 자동 대응, 단계별 실행 허가, 메모리 반환, 원자적 checkpoint를 구현한다.
- UI와 CLI를 연결하고, 4090 한 장만 노출한 상태로 전체 USD 경로를 검증한다.
- 모델 재사용은 보수적 프로세스 종료 경로부터 비교하며, 기존 경로보다 느려진 부분이 있으면 로딩·스케줄 비용을 기록해 해결한다.

### 2단계 — 단일 GPU 시간 단축

- 같은 단계에서 ERNIE·TRELLIS 모델 재사용. 동일 이미지의 rembg/conditioning 재사용.
- DINO 512/1024 처리를 한 번의 GPU 이동 구간으로 묶는다. 두 특징 계산은 그대로 유지한다.
- GLB 후처리를 cleaning/BVH/remesh/decimation/UV/raster/bake/inpaint/encode/write로 계측한다.
- 고정 mesh·고정 atlas로 실제 병목을 확인한 뒤 CPU 병렬 처리, 전송 통합, cache 등 출력 보존 최적화를 적용한다.
- RAM 여유에 따른 CPU 모델 상주와 첫 결과/처리량 우선 정책을 검증한다.

### 3단계 — 2 GPU 확장

- 1단계에서 확립한 같은 엔진에 GPU별 예약과 단계 겹치기 정책만 추가한다.
- CPU RAM 합산, 외부 GPU 점유, 느린 단계 앞의 큐 제한을 검증한다.
- 한 GPU가 사용 불가능해졌을 때 checkpoint를 활용해 신규/재개 작업을 단일 GPU 경로로 처리한다.
- 한 GPU 경로를 2 GPU 경로의 축소판으로 다시 구현하지 않는다. 기본 경로는 계속 유지한다.

### 4단계 — 기술이전 패키지와 운영 안내

- trellis2 기반 환경, 고정 패키지/모델/배포 패치 manifest, 상대 경로와 설정 예제, 설치 진단을 제공한다.
- 모델 파일을 모두 준비한 상태에서 네트워크 없는 실행을 검증한다. 누락 모델을 실행 중 자동 다운로드하는 동작에 의존하지 않는다.
- 검증된 GPU/VRAM/RAM별 지원표, 설정별 시간·피크 메모리, 알려진 제한을 제공한다.
- 내부망 UI의 진행 시간·대기 이유·재시도·실제 적용 품질 설정을 연결한다. 사용자는 GPU 번호나 offload 세부 항목을 일상적으로 조작하지 않아도 된다.
- 정상 생성, 중지, 재시도, 백업·복구, 진단 기록 수집을 인수 시나리오로 제공한다.

## 8. 검증과 완료 기준

### 자원·복구 검증

- GPU 한 장만 노출한 프로세스에서 물리 GPU가 원래 0이 아니어도 동작하고, 다른 GPU에는 모델을 올리지 않는다.
- 1 GPU/2 GPU, 다른 프로세스의 GPU 점유, RAM 부족, batch OOM, worker 비정상 종료, 중간 저장 실패, 디스크 부족을 구분해 처리한다.
- 메모리 제한 실험은 격리된 환경에서 수행한다. 예를 들어 64/96/128GB 조건을 확인하되 제한을 실제 적용할 수 없는 조건은 검증 완료로 표시하지 않는다.
- 최소 RAM 수치는 모델별 CPU RSS와 동시 실행 피크를 실제 측정한 뒤 확정한다. 현재 서버에서 성공한 사실만으로 수신 측 32/64GB 지원을 약속하지 않는다.
- checkpoint 재개 시 완료 결과 hash와 선택한 이미지·mesh·seed 대응을 확인한다. 재시작 후 완료 단계 시간이 늘어나지 않아야 한다.

### 품질·속도 검증

- 자동차·비행기·갈매기의 동일 입력/seed/프리셋을 기준으로 단일 GPU 기준선과 새 경로를 비교한다. 순수 후처리 변경은 mesh/atlas를 고정한다.
- 객체 1개, 복수 객체, UI 후보 2/3/4장, 서로 다른 객체 설명, ERNIE/Qwen INT8을 구분한다.
- 최초 결과 시간, 전체 완료 시간, 객체별 시간, 최대 메모리, 실패·재시도율을 측정한다. cold와 warm을 분리한다.
- 작은 A/B 실험은 조건별 최소 3회 반복한다. P95를 인도 수치로 제시하려면 동일 프로필의 충분한 표본(최소 30건)을 모으고 표본 수도 함께 기록한다.
- 단일 GPU의 안정성을 확보한 뒤 속도 개선을 채택한다. 2 GPU의 효과는 총 처리량과 첫 결과 지연을 각각 보고하며, 고정 배수의 향상을 미리 약속하지 않는다.
- 생성 원문·보강문·품질 설정이 유지되고, 다각도 외형·날개/다리·텍스처 seam·USD 연결과 수신 DCC 열기가 통과해야 한다. 병렬 연산/비결정적 후처리에 대해 픽셀·정점의 완전 동일성을 무조건 보장하지 않는다.

### 인도 완료

검증된 4090 한 장에서 처음 설치한 환경의 전체 생성·재시도·내부망 검토를 재현할 수 있고, 두 장에서도 같은 입력 계약으로 처리량이 개선되며, 각 환경의 지원 범위·측정값·복구 절차가 문서화된 상태를 완료로 본다.
