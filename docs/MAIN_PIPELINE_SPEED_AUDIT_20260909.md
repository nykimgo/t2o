# 메인 USD → 3D 에셋 파이프라인 시간 단축 분석

2026-09-09. 현재 로컬 코드, 설치된 TRELLIS.2/CuMesh/o_voxel, 기존 CSV 및 최근 작업실 계측 기록을 확인했다. 이 분석에서는 생성 코드·실행 환경을 변경하거나 새 GPU 실험을 수행하지 않았다. 메인 경로에 대한 새로운 단축률은 아직 실측되지 않았다.

## 결론

가장 큰 개선 후보는 **GLB 후처리**, 가장 명확한 구조 개선은 **T2I 모델 재사용·단계별 결과 재사용**이다. 2 GPU 환경에서는 객체 간 단계 겹치기도 유효하다. 샘플링 단계·형상 해상도·면 수를 먼저 낮추기보다 이 순서로 검증하는 편이 현재 품질을 보존하기 좋다.

현재 경로는 USD 파싱 → 전체 객체 LLM 정제 → TRELLIS.2 로드 → 객체별 [ERNIE subprocess → TRELLIS.2 → GLB 후처리] → 객체별 GLB→USD 변환·주입이다. UI에 추가한 후보 묶음 실행은 아직 메인 생성 경로에 연결되어 있지 않다.

- 후보 4장은 **동일한 보강문**을 공유한다. 메인의 서로 다른 객체 4개는 객체마다 보강·인코딩이 필요하므로, UI에서 얻은 단축률을 그대로 적용할 수 없다.

## 2. 우선순위별 개선 후보

### A. GLB 후처리 세분 계측과 최적화 — 잠재 효과 큼, 먼저 계측

근거: `previz_pipeline/trellis2_inference_core.py:323`, `patches/o_voxel/postprocess.py`. 설치된 o_voxel의 postprocess.py는 이 패치와 일치했다.

`save_time`은 파일 저장만이 아니다. 구멍 메우기 → BVH 생성 → 리메싱 → 면 수 감소 → UV 언랩 → UV 래스터화 → 원래 표면으로 투영 → 속성 샘플링 → 텍스처 빈 영역 채우기 → GLB 인코딩까지 포함한다. 따라서 디스크 속도만으로 설명할 수 없다.

먼저 이 구간을 각각 계측한다. 특히 CuMesh `uv_unwrap`은 GPU에서 chart를 만든 뒤 CPU로 옮기고, chart별로 xatlas 입력·패킹·결과 수집을 수행한다. CPU와 GPU가 섞여 있어 GPU 사용률이 낮다는 이유만으로 GPU를 추가해도 해결되지 않는다.

품질 유지 우선 후보:

- 리메싱·UV 언랩 결과를 캐시해, 텍스처 해상도 변경이나 저장 실패 재시도에서 앞부분을 재실행하지 않기.
- 동일 알고리즘의 텍스처 채널별 inpaint를 제한된 CPU 병렬도로 처리하는 실험. CPU thread 과다 사용과 RAM 증가도 함께 측정.
- 색·재질·알파의 GPU→CPU 복사를 한 번으로 모으고, 결과가 같은 배열 처리·저장 경로를 검증.
- UV 래스터화가 실제 병목일 경우에만 candidate 텐서 생성·메모리 대역폭·동기화 최적화. 현재 래스터라이저가 느린 원인이라고 단정하지 않는다.

`remesh=False`, UV chart 알고리즘 변경, inpaint를 다른 패딩 방식으로 교체하는 것은 형상·재질에 영향을 줄 수 있으므로 별도 품질 실험이다. 기존 배포용 구현을 유지한 상태에서 최적화한다.

기존 `experiments/uv_raster_swap/to_glb_split.py`에는 expensive prefix를 고정하는 실험 구조가 있다. UV 언랩·리메싱은 같은 입력에서도 비결정적이라는 기존 결과가 있으므로, bake 최적화는 **동일 UV atlas**를 양쪽에 넣어 비교한다.

### B. ERNIE 모델 재사용 — 구현 근거 확실, 효과는 객체 수에 비례

근거: `_t2i_generate()`가 객체마다 `subprocess.run()`으로 `text_to_image.py`를 실행한다 (`trellis2_inference_core.py:190`).

- 메인에서도 모델을 한 번 올리고 여러 객체를 처리하는 T2I worker를 사용한다.
- 같은 객체의 여러 seed 후보는 현재 UI처럼 보강문을 공유할 수 있다.
- 서로 다른 객체는 각자 정제·보강문을 유지한다. 속도를 위해 객체 외형 정보를 합치거나 category 단어만 쓰지 않는다.
- 서로 다른 길이의 보강문을 batching하면 padding/attention 비용과 VRAM도 달라지므로 별도로 측정한다.

TRELLIS.2는 이미 `manager.load_pipeline()`을 **한 실행의 객체 루프 전에 한 번** 호출한다. TRELLIS.2까지 매 객체마다 다시 로딩한다고 진단하면 틀리다. TRELLIS.2 상주화의 추가 이득은 주로 **다음 USD 요청에서도 재사용**할 때 생긴다.

### C. 재시도·재작업 체크포인트 — 불필요한 재생성 비용 감소

근거: 메인 `_generate_single()`에는 단계별 checkpoint 재개가 없고, 새 실행은 기본적으로 새 출력을 만든다. 생성 실패 레코드는 시간도 0으로 기록한다.

- 참조 이미지 → 전처리 이미지 → 이미지 conditioning → mesh/속성 volume → 정리된 mesh·UV → 최종 파일 단위로 완료 결과를 보존한다.
- GLB 저장만 실패하면 T2I·3D를 반복하지 않는다. USD 변환만 실패하면 검증된 GLB부터 재개한다.
- 같은 이미지로 3D seed만 재시도할 때 배경 제거와 DINO의 512/1024 특징을 재사용한다. 이미지가 바뀌면 반드시 무효화한다.
- cache key에는 실제 입력, 모델/가중치 버전, 프롬프트 규칙, seed, 생성 설정, 출력 설정을 단계별로 포함한다. 파일 존재 여부나 category만으로 서로 다른 외형을 같은 에셋으로 취급하지 않는다.
- 사용자가 '새로 생성'한 요청은 캐시 재사용 요청과 구분한다. 자동 재시도로 기존 참조 이미지·mesh의 대응이 어긋나지 않도록 각 시도와 선택 결과를 함께 보존한다.

이 최적화는 정상 첫 생성의 시간을 대폭 줄이는 방법이 아니라, 실패·반복 수정에서 시간을 회수하는 방법이다.

### D. TRELLIS.2 CPU↔GPU 이동 감소 — 비교적 작은 변경부터

근거: 현재 모델 설정에는 low_vram 명시가 없고 로더는 `True`로 기본 설정한다. 이 모드에서는 `.cuda()`가 모든 모델을 즉시 GPU에 상주시킨다는 의미가 아니다. 실제로 각 단계의 모델을 GPU에 올렸다가 CPU로 되돌린다.

- `run()`이 `get_cond(image, 512)`와 `get_cond(image, 1024)`를 연속 호출한다. `get_cond()`마다 DINO를 GPU로 올렸다가 CPU로 내린다. 두 인코딩을 한 번의 이동 구간에서 수행한 후 내리는 것이 첫 후보다.
- 512 특징으로 1024 특징을 대체하지 않는다. 두 계산을 그대로 수행하고 이동만 줄인다.
- 재시도 시 conditioning cache를 사용하면 같은 이미지의 특징 추출도 생략할 수 있다.
- 기본 1024_cascade는 512 형상 flow와 1024 형상·텍스처 flow를 사용하지만, 설정에는 512 텍스처 flow도 포함된다. 고정 배포 모드에서는 미사용 모델을 선택적으로 로딩할 여지가 있다. 다른 모드로 전환하는 요청을 고려해야 한다.
- `mesh.simplify(16777216)`는 모든 mesh에서 호출된다. 이미 목표보다 작은 경우에 내부 준비 비용을 조건부 생략할 수 있는지 확인한다. 후속 100만 면 리메싱과 목적이 다르므로 두 호출을 무조건 중복이라고 삭제하지 않는다.

`low_vram=False`를 단순히 켜서 모든 모델을 상주시키는 것은 4090 한 장에서 보장되지 않는다. 전체 가중치뿐 아니라 cascade 중간 tensor와 후처리 최대 VRAM을 함께 측정해야 한다.

### E. 객체 간 단계 겹치기 — 다중 객체 전체 처리량 개선

현재는 객체 A의 T2I→3D→GLB가 끝나야 B를 시작한다. 생성 전체가 끝난 뒤 USD 변환도 순서대로 수행한다.

- **1 GPU:** 참조 이미지들을 모아서 한 번의 T2I 모델 로딩으로 만들고, TRELLIS.2 단계로 넘기는 구성이 단순하다. 전체 참조 이미지를 먼저 만들면 첫 3D가 나오는 시점은 늦어질 수 있으므로 소량 그룹 처리와 비교한다. 두 모델의 CPU 메모리까지 포함해 residency 정책을 정한다.
- **2 GPU:** GPU A에서 다음 객체의 T2I를 준비하는 동안 GPU B에서 현재 객체의 3D와 GPU 후처리를 수행한다. 완성된 GLB의 USD 변환은 제한된 CPU worker에서 겹칠 수 있다.
- 동일 USD 레이어/같은 객체 파일에 대한 쓰기는 직렬화한다. 두 thread가 하나의 mutable pipeline을 공유하도록 단순 병렬화하지 않는다.
- 후처리가 긴 경우 T2I만 별도 GPU로 옮겨도 전체가 2배 빨라지지는 않는다. 정상상태 처리 간격은 대략 `max(T2I, I2O+후처리)`에 제한되며 시작·마무리 비용도 있다.
- T2I에서 4장 batching이 된다고 TRELLIS.2 서로 다른 객체도 4개 batching이 안전하다는 뜻은 아니다. 현재 `num_samples`는 한 이미지 조건의 복수 샘플이고, sparse token 수·복호화 메모리가 객체에 따라 달라진다.

### F. LLM 정제·USD 변환 — 우선순위 중간 이하

LLM 정제는 현재 이미 객체 목록을 한 번에 호출하므로 '한 객체씩 요청하니 batch로 바꾸자'는 진단은 맞지 않는다. 다만 요청 간 정제 캐시가 없고 큰 목록을 한 JSON으로 받는다. 정제 결과 캐시, bounded batch, 구조화된 출력과 누락 항목만 재시도하는 방식은 재작업을 줄일 수 있다. 문장 생성 조건 변경은 품질 비교가 필요하며 보강 OFF를 속도 개선으로 채택하지 않는다.

GLB→USD 변환은 이미 numpy→Vt bulk 경로를 사용한다. 다음 후보는 매 객체 Python process 시작의 제거, native converter가 보장한 경로를 다시 정규화하는 USD 재열기 제거, 텍스트 geometry.usda 대신 바이너리 geometry.usdc 실험이다. 마지막 변경은 파일명·참조와 수신 DCC 호환성을 확인해야 한다. 과거 3객체 변환은 총 18초로 후처리보다 비중이 작았다.

생성 3단계 밖의 자동 리깅도 확인했다. `autorigging/autorig.py`는 이미 batch daemon을 한 번 띄우고 완료 산출물을 건너뛴다. 모델 매번 로딩 제거를 새 이득으로 잡지 않는다. 생성과 리깅 동시 실행은 기존 RAM 문제 기록이 있어 이번 기본 개선안에 포함하지 않는다.

## 4. 측정 전 확인할 실제 불일치

1. **루트 런처 옵션:** `/home/sr/previs_proj/object_generate.sh:373`은 `--backend`를 전달하지만, 현재 `json_parse_and_inference.py`의 argparse에는 이 옵션이 없다. AST로 등록된 옵션 목록을 확인했다. 이 조합은 인자 파싱 오류를 일으키므로 메인 E2E 측정 전에 진입점 계약을 맞춰야 한다. `t2o_pipeline/run_usd_to_3D_object.sh`는 해당 인자를 전달하지 않는다. 분석 중 이를 수정하지 않았다.
2. **실측 조건:** CLI 텍스처 기본 1024, UI 2048, 과거 FLUX vs 현재 ERNIE, cold 모델 준비 포함 여부를 고정해야 한다.
3. **계측 누락:** 메인의 객체 CSV 합계에는 최초 모델 로딩·LLM·USD 변환이 전부 포함되지 않고, 실패 레코드는 시간 0이다. 깊이붕괴 때문에 T2I를 다시 실행한 시간은 현재 I2O 블록에 합쳐진다. 성공 객체 평균만으로 개선 효과를 판단하면 오해할 수 있다.
4. **이미 적용된 개선:** 프리뷰 렌더 제거, scene canonical/shot override 중복 제외, USD numpy bulk 변환은 현재 코드에 존재한다. 과거 문서의 개선분을 새 개선 예상치에 다시 더하지 않는다.

## 5. 권장 진행 순서와 성공 기준

1. 런처 계약·실행 설정을 확정하고 전체/세부 구간 타이머를 통합한다. startup, LLM, 모델 로딩, PE, encoding, rembg, conditioning, 구조/형상/텍스처 sampling·decode, 후처리, USD, 실패/재시도를 분리한다.
2. **고정 mesh의 후처리만** 먼저 측정한다. 기존 mesh.npz를 이용하면 T2I·TRELLIS를 재실행하지 않고 가장 긴 구간을 조사할 수 있다. UV bake 비교에서는 atlas까지 고정한다.
3. T2I worker 재사용과 단계별 checkpoint를 메인에 연결한다. 같은 이미지의 rembg/conditioning 재사용과 DINO 왕복 제거를 검증한다.
4. CPU UV·inpaint와 GPU bake 중 실제 지배적인 구간을 최적화한다. 이후 1 GPU 묶음 처리와 2 GPU 단계 겹치기를 비교한다.
5. 그래도 필요하면 면 수·텍스처·sampling 변경을 별도 품질 프리셋 실험으로 진행한다.

비교 대상은 자동차·비행기·갈매기처럼 서로 다른 형상에 고정 입력/seed를 사용한다. cold 1회와 warm 반복을 분리하고 각 조건을 최소 3회 측정한다. 최초 결과까지 시간, 객체당 시간, 전체 완료 시간, p50/최댓값, GPU별 VRAM, CPU RSS, 실패·재시도 비율을 함께 기록한다. 1 GPU와 2 GPU 결과를 분리한다.

동일 계산·재사용 변경은 선택된 참조 이미지와 설정 대응이 유지되는지 확인하고, mesh/UV 비결정성 때문에 동일성 검사가 어려운 단계는 고정 중간 산출물을 대조한다. 품질 변경은 다각도 렌더·실루엣·텍스처 seam과 필요한 평가 지표로 별도 승인할 근거를 만든다. 기존 성공 결과·USD 원본은 실험용 사본으로 보호한다.
